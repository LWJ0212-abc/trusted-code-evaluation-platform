# 提交评测事件契约开发指南

本文按项目现有架构说明评测事件 DTO、事件消费目录和契约测试。事件 JSON 的唯一权威来源是仓库根目录 `docs/事件契约.json`；本文不另建一套事件名或字段。可直接用于契约验证的样例位于 `docs/fixtures/events/`。

## 1. 当前阶段和边界

M0-B 的 Server 受理事务原子写入 `submission`、首个 `evaluation_task` 和 `outbox_event`。Outbox 发布 `evaluation.requested`。消费端校验事件、登记 Inbox 并核验已存在的提交和任务事实；重复消息不能再创建一条 submission 或 evaluation task。

M0-B 不运行用户代码，也不实现 Worker 沙箱。Worker 后续按相同 JSON Schema 消费评测请求并执行任务。Worker 的执行尝试、租约和运行结果不能与 Server 的提交受理事实混为一类记录。

| 事实/类型 | 归属位置 | 说明 |
| --- | --- | --- |
| `SubmissionStatus` | `server.submission.domain` | Server 提交记录的业务状态 |
| `EvaluationTask` | 按当前 M0-B 实现指南属于提交受理领域 | 受理事务创建的持久评测任务事实 |
| 事件 DTO、Schema 校验、Inbox 消费 | `server.evaluation.infrastructure` | 传输和消费基础设施，不承载领域状态机 |
| Outbox 发布 | `server.outbox` | 可靠发布，不直接操作评测领域状态 |
| Worker 执行尝试 | 后续 `Worker` 应用 | 不在当前 Server `evaluation` 目录实现 |

事件中的 `aggregate_id` 对应被推进状态的聚合。`evaluation.requested` 和 `result.accepted` 都使用 `evaluation_task_id`；两者 payload 中的 `evaluation_task_id` 必须与 `aggregate_id` 相同。`aggregate_revision` 是该任务持久化的非负 bigint revision，以十进制字符串传输。任务创建时 revision 为 `0`，每次任务状态或任务事实发生并发可见的变更时递增；事件携带其所描述状态对应的 revision。M0-B SQL 因此包含 `evaluation_task.revision`。生产者生成的 `occurred_at` 固定使用 UTC RFC 3339 时间，并以 `Z` 结尾；JSON Schema 的 `date-time` 格式检查之外，生产者/消费者契约测试也要断言 UTC `Z` 形式。

任务代次：当前 v1 事件不包含 `generation`。自动基础设施重试是在同一个 `evaluation_task` 下创建新的 `execution_attempt`；人工重评为同一 submission 创建新的 `evaluation_task`，并以新的 `evaluation_task_id` 区分。租约栅栏使用任务的 `lease_epoch`，不以 event ID 或 submission ID 代替。

## 2. 当前事件

### `evaluation.requested`

含义：Server 已受理提交，并在数据库中持久化了对应 submission、evaluation task 和 Outbox 事件。它通知调度器重读已存在的 task 并尝试租约，不表示评测已开始或完成。重复事件不能新建任务。

当前 v1 信封必填字段：

| 字段 | JSON 类型 | 规则 |
| --- | --- | --- |
| `event_id` | UUID 字符串 | 稳定唯一；重投时不变，用于 Inbox 去重 |
| `event_type` | 字符串 | 固定为 `evaluation.requested` |
| `schema_version` | 整数 | 固定为 `1` |
| `occurred_at` | 日期时间字符串 | RFC 3339/ISO-8601 时间 |
| `aggregate_id` | UUID 字符串 | 评测任务聚合 ID，必须等于 payload 中的 `evaluation_task_id` |
| `aggregate_revision` | 十进制字符串 | 非负 bigint，避免 JSON 数字精度损失 |
| `trace_id` | 非空字符串 | 仅用于链路追踪，不用于授权 |
| `payload` | 对象 | 精确字段见下表 |

`payload` 字段：

| 字段 | JSON 类型 | 规则 |
| --- | --- | --- |
| `submission_id` | UUID 字符串 | 必须与 `aggregate_id` 对应的提交一致 |
| `evaluation_task_id` | UUID 字符串 | 引用受理事务已经创建的 task |
| `content_version` | UUID 字符串 | Worker 必须使用该不可变内容版本 |
| `batch_id` | UUID 字符串或 null | 当前普通提交为 null；其他场景按 schema 定义 |

Schema 当前使用 `additionalProperties: false`，因此 v1 消息不能自行添加 `generation`、`input_ref` 等字段。事件必须使用契约中规定的全部必填字段。

源码读取：Worker 不直连业务数据库。Worker 先通过受控任务/租约端点取得任务级短期授权，再经对象访问代理读取该任务明确引用的源码对象；授权不得允许列举 bucket 或读取其他提交。事件不携带对象存储凭据、源代码正文或长期签名 URL。

### `result.accepted`

含义：结果接收方接受了一份已持久化的评测结果。它不是通用的 Worker 完成通知；结果引用、内容版本、摘要和批次必须符合 JSON Schema 与业务事实。

必填 payload 字段为：

| 字段 | JSON 类型 | 规则 |
| --- | --- | --- |
| `evaluation_task_id` | UUID 字符串 | 关联已知评测任务 |
| `evaluation_result_id` | UUID 字符串 | 已持久化评测结果的标识 |
| `content_version` | UUID 字符串 | 结果所基于的内容版本 |
| `result_digest` | 64 位小写十六进制字符串 | 用于校验结果内容一致性 |
| `batch_id` | UUID 字符串或 null | 关联批次；无批次时为 null |

外层使用与 `evaluation.requested` 相同的信封字段，具体约束以 JSON Schema 为准。不得把完整日志、测试输入、源代码或凭据放进事件。

## 3. Java 类型放置

当前 Server 的事件 DTO 按既有实现指南放在：

```text
src/main/java/lwj/code/server/evaluation/infrastructure/
  EvaluationRequestedEvent.java
  EvaluationRequestedConsumer.java
  InboxEntity.java
  InboxMapper.java
```

`EvaluationRequestedEvent` 可以用 Java `record` 表示不可变 JSON 数据。它是 JSON DTO，不是 `Submission`/`EvaluationTask` 领域对象，也不负责发送 RabbitMQ、查询数据库或推进状态。DTO 字段、类型和序列化名必须与 JSON Schema 一致。

事件消费者负责：

1. 校验 `event_type`、`schema_version`、必填字段和格式。
2. 在本地事务内按 `(consumer_name, event_id)` 登记 Inbox。
3. 核对 submission、evaluation task、内容版本和批次引用。
4. 对重复事件幂等处理；不创建第二个 submission 或 evaluation task。
5. Inbox 和处理结论提交成功后才 ACK RabbitMQ。

Worker 尚未实现时，不要让 Server `evaluation.infrastructure` 变成编译/运行代码的模块。以后 Worker 可有自己的传输 DTO，但必须用同一 Schema/fixture 验证；不要让 Worker 依赖 Server 的领域包。

## 4. 版本和兼容规则

- v1 以 `(event_type, schema_version)` 识别，例如 `("evaluation.requested", 1)`。
- JSON Schema 是字段、类型、必填性和额外字段策略的唯一依据；消费者不得只凭 Java 反序列化成功就认定消息有效。
- 不兼容的字段或语义变更发布新 `schema_version`，并先部署能处理新版本的消费者。
- 未知事件类型/版本、缺少必填字段或格式错误不能静默 ACK 丢弃；应进入隔离/DLQ 并告警。
- Outbox 重发使用原 `event_id` 和原 payload。RabbitMQ 至少一次投递，消费者必须幂等。
- `occurred_at` 不保证事件顺序；使用 `aggregate_revision` 和数据库条件更新识别过期或乱序事件。
- 不把 Redis 用作 Inbox、幂等事实、Outbox 或任务状态的替代品。

## 5. 按步骤完成

### 步骤 1：检查 JSON Schema

打开根目录 `docs/事件契约.json`，找到 `evaluation.requested` 和 `result.accepted` 两个分支。逐项记录 envelope/payload 的字段、类型、必填性和 `additionalProperties` 规则。字段若与 Java DTO 或本文示例不同，以 JSON Schema 为准，并先修订契约再写实现。

完成标准：字段清单与 Schema 一致；没有额外自行约定的字段。

当前定稿规则：自动重试不增加 task ID；人工重评创建新 task ID；v1 不传 `generation`。源码由 Worker 通过任务级短期授权和对象访问代理读取。`evaluation.requested` 与 `result.accepted` 都以 task 为聚合，使用 task ID 和 task revision。

### 步骤 2：确定 Java DTO 路径

Server 当前使用 `server.evaluation.infrastructure`。创建 `EvaluationRequestedEvent` 及必要的 payload record；若也需要 Server 接收 `result.accepted`，再按实际消费者增加对应 DTO。不要把消息 record 放进 `submission.domain`，也不要因为 Server/Worker 尚未共享构建而提前引入整个 EventContracts Maven 模块。

完成标准：DTO 只表示契约数据，不依赖 MyBatis Entity、RabbitMQ SDK 或其他服务领域对象。

### 步骤 3：固定序列化行为

明确 JSON 使用 snake_case，Java 使用 camelCase；在 DTO 注解或明确配置中实现映射。UUID、日期时间、bigint revision 和 nullable `batch_id` 按 Schema 规则序列化。不要依赖 Server 与 Worker 恰好使用相同的全局 Jackson 配置。

完成标准：Java DTO 序列化后的字段名、JSON 类型和 null 行为与 Schema 一致。

### 步骤 4：编写契约测试

使用 `docs/fixtures/events/evaluation-requested.v1.json` 和 `docs/fixtures/events/result-accepted.v1.json`，按 `docs/事件契约.json` 测试：

- 合法 `evaluation.requested` 和 `result.accepted` 可通过 Schema 校验。
- 缺字段、错误 UUID、错误 revision、错误 digest、未知版本会失败。
- v1 中额外字段会按 `additionalProperties: false` 拒绝。
- Java record 与 JSON fixture 可双向序列化，`batch_id: null` 保持为 JSON null。
- `occurred_at` 由生产者输出为 UTC RFC 3339 且以 `Z` 结尾。
- `aggregate_id`、`submission_id`、`evaluation_task_id` 等关系由业务校验器核对。
- 同一个 `event_id` 重复消费只产生一次副作用；消费事务成功而 ACK 丢失后重投仍幂等。

若 Worker 独立构建，将相同 fixture 和 Schema 校验测试加入 Worker；不能只测共享 DTO 而忽略两端实际序列化配置。

完成标准：更改字段名、类型、必填性或版本而未同步契约时，测试会失败。

### 步骤 5：完成消费决策表

| 输入情况 | 处理 |
| --- | --- |
| 首次收到合法 `evaluation.requested` | Inbox 去重并核验已存在 task；成功持久化后 ACK |
| 相同 `event_id` 再次投递 | 不重复副作用，ACK |
| 不同 event ID 指向同一个 task | 依靠 task 事实/唯一约束识别重复，不创建新 task，并记录诊断信息 |
| 缺字段、未知版本或非法格式 | 不应用业务副作用；进入有界重试或 DLQ，告警 |
| task/submission 不存在或版本不一致 | 不伪造任务；按 Schema/业务错误策略隔离并告警 |
| 过期 `aggregate_revision` | 不覆盖更新事实；幂等记录后 ACK 或隔离，按该事件消费者规则执行 |

### 代码结果、系统失败与状态映射

| 情况 | 任务/尝试状态 | submission 状态 | 事件处理 |
| --- | --- | --- | --- |
| 有可信代码结果，包括编译错误、答案错误、超时、资源限制或安全拦截 | `RESULT_REPORTED -> GRADING -> GRADED` | `RUNNING -> GRADING -> FINISHED` | 结果接收成功后发布 `result.accepted`；具体结果码保存在结果事实中，不扩充该事件 payload |
| 暂时基础设施故障 | `INFRA_FAILED/WORKER_FAILED -> RETRYING -> QUEUED` | `RUNNING -> RETRY_WAIT -> QUEUED` | 创建/领取新 execution attempt；不发布 `result.accepted` |
| 基础设施尝试耗尽且没有当前可信结果 | `DEAD_LETTER` | `SYSTEM_FAILED` | 不发布 `result.accepted`，也不能伪装成 0 分 |
| 结果已接受，但评分暂时失败 | `GRADING` 并恢复评分 | `GRADING` | 不回到代码执行，不把提交改成 `SYSTEM_FAILED` |

基础设施尝试耗尽且没有可信评测结果时，任务持久化为 `DEAD_LETTER`，submission 持久化为 `SYSTEM_FAILED`，由查询接口向用户和运维人员展示失败分类与可重试/人工处理信息。本阶段不新增 `evaluation.failed`：它会引入第二个失败通知事实及其重投、去重和状态所有权问题，而查询接口已经能读取权威持久状态。需要异步通知或跨服务订阅系统失败时，再评估新增版本化失败事件；该事件不能替代数据库状态。

完成标准：基础设施系统失败可通过持久化任务和 submission 查询；没有可信结果时不发布 `result.accepted`，也不伪装为零分。

完成标准：每种输入都明确为应用、幂等忽略或隔离，不依赖开发者临时猜测。

## 6. 本阶段完成清单

- [ ] 事件名使用 `evaluation.requested` / `result.accepted`，与现有 Schema 一致。
- [ ] JSON Schema 是唯一契约来源，字段没有未经批准的偏差。
- [ ] `EvaluationRequestedEvent` 放在 `server.evaluation.infrastructure`。
- [ ] `SubmissionStatus` 和 `EvaluationTask` 仍按现有领域划分，不与传输 DTO 混用。
- [ ] Inbox 使用 `(consumer_name, event_id)` 去重，并与本地处理结论事务提交。
- [ ] 重复、乱序、未知版本、缺字段和事实不匹配都有明确处理规则。
- [ ] DTO/fixture/schema 有契约测试。

完成后再进入 Outbox 与 RabbitMQ Relay/Consumer 实现。Redis 缓存和限流不属于事件契约工作。
